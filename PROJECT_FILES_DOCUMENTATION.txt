1. SYSTEM ARCHITECTURE & DATA FLOW OVERVIEW
================================================================================

Civic Issue Resolution Platform (CIRP) is an enterprise-grade municipal governance and issue resolution system. It connects four distinct stakeholders:
1. Citizens (reporting issues, tracking tickets, verifying fixes, rating service)
2. Municipal Administrators & SuperAdmins (triaging, assigning crews, setting SLAs)
3. Department Officers (routing, monitoring department performance)
4. Field Workers / Crews (executing on-site 3-phase repair work with geo-tag proofs)

CORE TECHNICAL PILLARS:
- Frontend: React 18, Vite, React Router DOM, Tailwind CSS, Lucide React icons.
- Backend: Node.js (ES Modules), Express.js REST API, Socket.IO WebSockets.
- Database: MongoDB Atlas (Mongoose ODM) with 2dsphere Geospatial indexing.
- Geolocation & Mapping: 100% Google Maps JavaScript SDK, Google Places Autocomplete API, Google Geocoding API.
- Photo Integrity: Binary EXIF parser (exifReader.js) extracting camera GPS tags (Latitude, Longitude, Altitude, Timestamp, GPS Camera App signature).
- SLA Automation: Node-cron background service evaluating deadlines every 15 minutes.

16. server/src/models/Issue.js
    - What it is: Mongoose schema representing civic issues and tickets.
    - Why it is used: The central data repository for every reported civic problem.
    - How it works inside:
      * Core Fields: issueNumber (unique indexed ticket ID e.g. HYD-2026-0001), title, description, category (ref: IssueCategory), priority (urgent, high, medium, low), status (submitted, verified, assigned, in_progress, resolved_verification_pending, closed, rejected, reopened, withdrawn).
      * Geospatial Location: GeoJSON Point schema ({ type: 'Point', coordinates: [lng, lat] }) with a 2dsphere index for spatial proximity queries; landmark, address, serviceArea (ref: ServiceArea).

      * Multi-Worker Team Roster: "assignedWorkers: [{ worker: ref: User, role: String, note: String, assignedAt: Date }]".
      * 3-Phase Work Execution: "executionPhases: { startingPhase: { startedAt, note, images: [{ url, geoTag }] }, duringPhase: { inProgressAt, note, images: [{ url, geoTag }] }, completionPhase: { completedAt, note, images: [{ url, geoTag }] } }".
      * SLA Tracking: slaDeadline, slaHours, isEscalated, escalatedAt.
      * Timeline & Audit Logs: Array of events recording every status change, worker assignment, note, performedBy user ID, and timestamp.
      * Citizen Feedback: rating (1-5 stars), comment, closedAt.

21. server/src/controllers/adminController.js
    - What it is: Business logic for Municipal Administrators and SuperAdmins.
    - Why it is used: Handles verification, rejection, routing, team assignments, and phase proof reviews.
    - How it works inside:
      * "verifyIssue(req, res)": Transitions issue status from 'submitted' to 'verified', records timeline entry, and notifies the citizen.
      * "rejectIssue(req, res)": Validates rejection category and explanation, transitions status to 'rejected', and updates audit trail.
      * "assignDepartmentAndWorker(req, res)": Assigns department, primary worker, recalculates slaDeadline (now + slaHours), sets status to 'assigned', and emits real-time alert to the worker.
      * "addWorkerToRoster(req, res)": Appends worker ID, specialized role (e.g., Heavy Equipment Operator), and dispatch instructions into issue.assignedWorkers; creates audit log and notifies the worker.
      * "removeWorkerFromRoster(req, res)": Filters out a worker from issue.assignedWorkers and logs the removal to timeline.
      * "submitPhaseProof(req, res)": Accepts phase ('starting', 'during', 'completion'), saves geo-tagged photos and notes into issue.executionPhases, appends photos to evidence, updates timeline, and emits socket event.

22. server/src/controllers/issueController.js
    - What it is: Controller for citizen-facing issue operations.
    - Why it is used: Handles issue creation, searching, upvoting, confirmation, reopening, and withdrawal.
    - How it works inside:
      * "createIssue(req, res)": Generates unique issue number via issueNumberGenerator.js, stores GeoJSON coordinates and EXIF GPS verification flag, pushes initial photo evidence, invokes "notifyAdminsOnNewIssue()", and emits real-time "issue:created" event to all administrators.
      * "getIssues(req, res)": Parses query parameters (status, category, search, priority, page, limit), builds Mongoose filter, executes paginated find() with populate(), and returns items with total page count.
      * "toggleUpvote(req, res)": Atomically adds or removes user ID from issue.upvotes array and returns updated count.
      * "toggleFollow(req, res)": Adds/removes user ID from issue.followers array.
      * "confirmResolution(req, res)": Citizen rates resolution (1-5 stars), adds feedback note, transitions status to 'closed', and marks ticket resolved.
      * "reopenIssue(req, res)": Validates citizen's reopen explanation and defect photos, transitions status back to 'reopened', resets SLA timer, and notifies administrators for re-dispatch.
      * "withdrawIssue(req, res)": Allows reporter to cancel a ticket, transitioning status to 'withdrawn'.
      * "deleteIssue(req, res)": Permanently removes unverified/withdrawn reports.

23. server/src/controllers/workerController.js
    - What it is: Business logic for field workers.
    - Why it is used: Powers the field worker portal, task queues, and repair status submissions.
    - How it works inside:
      * "getAssignedTasks(req, res)": Queries issues where the user is either the primary assignedWorker OR listed in assignedWorkers team roster; calculates active, in_progress, and overdue task metrics.
      * "startWork(req, res)": Verifies user is assigned to the ticket, transitions status to 'in_progress', logs startWork timestamp and notes to timeline.
      * "addProgressUpdate(req, res)": Appends stage progress photos, logs materials used (e.g. 50kg asphalt), and records timeline entry.
      * "resolveTask(req, res)": Validates mandatory resolution proof photos and summary, sets status to 'resolved_verification_pending', records repair cost, and triggers notification to the citizen for closure.

4.4 API & Google Maps & EXIF Services (client/src/services/ & client/src/utils/)
--------------------------------------------------------------------------------

75. client/src/services/api.js
    - What it is: Axios HTTP API client module.
    - Why it is used: Centralizes all backend network requests with automatic JWT Bearer token attachment and 401 token refresh interception.
    - How it works inside:
      * Creates an Axios instance pointing to VITE_API_URL.
      * Request Interceptor: Injects "Authorization: Bearer <token>" from localStorage.
      * Response Interceptor: If a 401 error occurs, attempts to call "/auth/refresh" to obtain a new token and retries the original request.
      * Exports structured modules: authAPI, issueAPI, adminAPI, workerAPI, configAPI, uploadAPI.

76. client/src/services/googleMapsLoader.js
    - What it is: Singleton Google Maps JavaScript SDK loader.
    - Why it is used: Loads Google Maps dynamically with Places and Geocoding libraries.
    - How it works inside:
      * "loadGoogleMaps()": Injects script tag "https://maps.googleapis.com/maps/api/js?key=...&libraries=places" once and returns a cached Promise.
      * "searchGooglePlaces(query)": Uses Google Places AutocompleteService to return location suggestions.
      * "getPlaceDetails(placeId)": Resolves placeId to exact lat/lng coordinates and formatted address.
      * "reverseGeocode(lat, lng)": Uses google.maps.Geocoder to resolve coordinates to Indian street addresses.

77. client/src/utils/exifReader.js
    - What it is: Pure JavaScript binary EXIF parser.
    - Why it is used: Extracts GPS metadata directly from camera photos without third-party server dependencies.
    - How it works inside:
      * Reads File into an ArrayBuffer using FileReader.
      * Inspects JPEG markers: looks for Start of Image (0xFFD8) and APP1 EXIF marker (0xFFE1).
      * Parses TIFF header (Endianness: II / MM).
      * Locates GPS IFD pointer and extracts:
        - GPSLatitude & GPSLatitudeRef (N/S) -> converts degrees/minutes/seconds rational values to decimal latitude.
        - GPSLongitude & GPSLongitudeRef (E/W) -> converts degrees/minutes/seconds rational values to decimal longitude.
        - GPSAltitude, GPSTimeStamp, and Software (e.g., GPS Map Camera).
      * Returns { hasGeoTag: true, latitude, longitude, altitude, timestamp, software }.

6. STEP-BY-STEP COMPLETE ISSUE LIFECYCLE & INTERNAL MECHANICS
================================================================================

PHASE 1: CITIZEN REPORTING & EXIF AUTO-LOCK
--------------------------------------------------------------------------------
1. Citizen opens ReportIssuePage.jsx and attaches a site photograph.
2. exifReader.js parses JPEG binary markers, extracts GPS coordinates and camera app signature.
3. If GPS tags exist:
   - Google Map automatically centers on the photo coordinates.
   - Sets isGpsVerified = true.
   - Displays "EXIF Camera GPS Verified" badge.
4. Citizen chooses Category (e.g. Roads), adds description & landmark, and clicks Submit.
5. POST /api/issues sends payload to backend. issueController.js generates unique ID (HYD-2026-0001) and saves record in MongoDB Atlas.
6. notificationService.js immediately broadcasts "issue:created" via Socket.IO to all Administrators and SuperAdmins.

PHASE 2: MUNICIPAL REVIEW & MULTI-WORKER ROSTER DISPATCH
--------------------------------------------------------------------------------
1. Administrator opens AdminReviewQueuePage.jsx and reviews ticket details and photo geo-tags.
2. Admin clicks "Verify Issue": transitions status to 'verified'.
3. Admin clicks "Dispatch & Assign":
   - Selects Department (e.g. Roads Dept).
   - Selects Primary Worker and sets SLA target (e.g. 48 hours).
   - Status updates to 'assigned', and worker receives instant alert.
4. For complex repairs, Admin opens IssueDetailPage.jsx -> "Field Response Team" card -> "+ Add Worker":
   - Adds specialized workers (e.g. Excavator Operator, Safety Specialist) with dispatch notes.
   - POST /api/admin/issues/:id/workers appends crew members into assignedWorkers array.

PHASE 3: 3-PHASE FIELD WORK EXECUTION & PROOF SUBMISSION
--------------------------------------------------------------------------------
1. Field worker logs in to WorkerDashboardPage.jsx, sees task with active SLA countdown.
2. Worker clicks "Start Work": status transitions to 'in_progress'.
3. Phase 1 (Starting Phase):
   - Worker arrives at site, opens IssueDetailPage.jsx, clicks "+ Phase 1 (Starting)".
   - Uploads site arrival photo (EXIF GPS verified) with arrival note.
   - Saved to issue.executionPhases.startingPhase.
4. Phase 2 (During Phase):
   - Worker conducts repairs (excavation, asphalt laying), clicks "+ Phase 2 (During)".
   - Uploads in-progress photo with note on materials used.
   - Saved to issue.executionPhases.duringPhase.
5. Phase 3 (Completion Phase):
   - Worker finishes repair, clicks "+ Phase 3 (Complete)".
   - Uploads final completion photo and repair summary.
   - Saved to issue.executionPhases.completionPhase.
6. Worker clicks "Submit Resolution Proof": status updates to 'resolved_verification_pending', and citizen is notified.

PHASE 4: CITIZEN VERIFICATION & CLOSURE
--------------------------------------------------------------------------------
1. Citizen receives real-time alert and opens IssueDetailPage.jsx.
2. Citizen reviews Before/After comparison slider and 3-Phase photo proofs.
3. If satisfied: Citizen rates service (1 to 5 stars), adds feedback, and clicks "Confirm Closure". Status updates to 'closed'.
4. If defective: Citizen clicks "Reopen Ticket", specifies defect reason and attaches defect photo. Status transitions back to 'reopened' for municipal re-dispatch.
